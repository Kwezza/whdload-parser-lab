## Purpose

This document hands over the current state of the standalone `dat_to_tlv` effort so a new agent can resume without re-discovering the session history.

The goal of this work was to turn the staged variant-selection extraction into a self-contained DAT-to-TLV converter that can be built locally from `variant_backport_staging` without compiling against source files outside that folder.

## Current Status

What is working:

- Host build works.

- TLV output generation works on host.
- Amiga build now compiles and links successfully.
- The staging Makefile supports both host and Amiga targets.
- The staging Makefile has a `help` target.
- The staging Makefile does not use PowerShell in normal build rules.

What is not working:

- The Amiga binary reportedly crashes at runtime.
- The exact crash site is not yet confirmed in this session.

Likely crash window in `app_src/main.c`:

5. `tlv_record_init(&aggregate)` and aggregate merge
6. output file creation / TLV write

Because the log only shows the initial startup line, the next agent should assume the crash occurs somewhere after `append_to_log("Standalone DAT-to-TLV run starting ...")` and before the final success summary.

## Design Choices Made In This Session

These should be preserved unless there is a specific reason to change them.

1. Host-first validation was chosen before worrying about Amiga runtime issues.
2. The standalone tool builds only from files inside `variant_backport_staging`.
3. The implementation is intentionally narrow: DAT -> parsed filenames -> aggregate TLV.
4. Profile-based filtering and variant scoring were intentionally not integrated into the standalone runner yet.
5. The DAT parser is a minimal local parser, not the full `xml_parser.c` dependency tree.
6. The Makefile avoids PowerShell for normal build rules.

## Recommended Next Debugging Steps For The New Agent

The highest-value next work is to isolate the Amiga runtime crash.

Suggested order:

1. Add granular logging checkpoints in `app_src/main.c` after each major step:
   - after DAT parse
   - after pack type load
   - after `tlv_session_init`
   - after batch processing
   - after aggregate creation
   - after output file open
   - after TLV write

2. Add record-count or progress logging for the first few iterations of `tlv_session_process_batch` to see whether the crash happens early or only after many records.

3. Verify path assumptions on Amiga:
   - `assets_raw/Games(19-05-2025).dat`
   - `assets_raw/defs`
   - `assets_raw/prefs/pack_types.ini`
   - `output/Games(19-05-2025).tlv`

4. Check whether `whd_mkdir("output")` and relative path resolution behave the same way on the Amiga runtime as on host.

5. Check whether memory pressure is the actual cause:
   - 3861 filenames
   - one `TLV_Record` per input
   - aggregate record merge after batch processing
   - this may be much heavier on a real Amiga than on host

6. If memory is suspected, test a small DAT subset first or add a temporary limit parameter to process only the first N entries.

7. If the crash occurs before batch processing, focus on:
   - `parse_dat_filenames_minimal`
   - `load_pack_types`
   - `build_field_registry_from_ini`
   - `csv_cache_manager_init`

8. If the crash occurs later, focus on aggregate growth and large allocations in:
   - `tlv_record_init`
   - `tlv_record_add_entry`
   - `merge_record_into_aggregate`

## Suspicion List

These are not confirmed bugs, only the most plausible crash surfaces.

- Large memory footprint on Amiga due to storing all filenames, all per-file TLV records, and one merged aggregate record at once.
- Relative path behavior differences on Amiga for `assets_raw/...` and `output/...`.
- File or directory creation differences on Amiga in `ensure_default_output_directory()`.
- A hidden host-friendly assumption in one of the portable modules that only fails under vbcc/runtime behavior.

## If The Next Agent Wants A Smaller Probe

The fastest low-risk debugging move is probably:

1. instrument `main.c` with more `append_to_log()` checkpoints
2. add a temporary hard cap like `process only first 10 or 50 DAT entries`
3. rerun on Amiga
4. confirm whether the crash is immediate or scale-related

That will likely cut the search space much faster than broad refactoring.
